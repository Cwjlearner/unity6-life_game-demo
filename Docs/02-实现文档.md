### 3.1 接口为什么没有 `GetCell`

GPU 实现无法同步回答"某个细胞是死是活"——那需要把显存搬回内存。因此 `IGridKernel` 只提供 `Snapshot()`；CPU 实现顺带提供 `GetCell`/`SetCell` 作为便利方法（测试与盖印用），但不放进契约里。**接口的形状不要迁就单条实现路径**，这是这次分层里唯一一处刻意的取舍。

## 4. CPU 参考实现细节【已实现】

### 4.1 规则与存储

- 规则：`B3/S23`，即死细胞恰好 3 个活邻居时诞生；活细胞有 2 或 3 个活邻居时存活，否则死亡。
- 存储：`bool[W*H]` 当前 + `bool[W*H]` 下一代的整格双缓冲。每代结束用 `Array.Copy` 交换。
- 邻居统计：直接 `for dy in [-1,1] for dx in [-1,1]` 累加，读邻居统一走 `GetCell`，由它负责边界语义。

这份实现**故意不优化**。"可读的、一眼看出正确的基线"比"快一点但需要仔细推敲的代码"更有价值——它的产出是哈希和断言，不是帧率。

### 4.2 边界语义

| 模式 | 越界读取 | 越界写入 |
|---|---|---|
| 环面（默认） | 回绕到对侧 | 抛异常（写入必须显式合法） |
| 死边界 | 返回 false（视为死细胞） | 抛异常 |

写入越界**抛异常而不是静默裁剪**：盖印构型时如果坐标算错，静默裁剪会得到一个"看起来还能跑"的错误画面，而异常立刻指出问题。

### 4.3 状态快照与哈希

`GridSnapshot` 用位打包存储（`ulong`，行主序，低位在前），提供两种构造入口：

- `FromCells(...)`：CPU 路径；
- `FromPackedBits(...)`：GPU 回读路径，按 **32 位**行宽（`wordsPerRow = ceil(W/32)`）重新排布到 `ulong` 字。

第二种转换是 CPU/GPU 交叉验证的地基，已用宽度 37（非 32 的倍数，覆盖行尾填充）的用例验证过等价性。

哈希采用 FNV-1a，**只覆盖细胞位，不含代数**——这是"周期 n 后是否回到原状态"能被哈希判定的前提。

### 4.4 行为判定

```csharp
// 平移判等：b 是否等于 a 平移 (dx,dy) 后的结果
PatternCompare.MatchesTranslated(a, b, dx, dy, wrapEdges)

// 运行期检测：返回最小周期与每周期位移，要求连续两个周期都成立
PatternCompare.TryDetectPeriod(history, maxPeriod, maxDisplacement, out period, out displacement)
```

`TryDetectPeriod` 要求**连续两个周期**都成立才采纳，避免"恰好某一步撞上"的假阳性。

## 5. GPU 管线设计【已实现：基础版】

本节全部内容已实现：5.1 乒乓纹理、5.2 基础 kernel、5.3 三档优化、5.4 盖印、5.5 / 5.6 档二与档三的坑。四档均通过 GPU 一致性测试。

### 5.1 乒乓纹理

```csharp
// 两张同规格纹理；enabledRandomWrite = true、无 mipmap、Point 过滤
RenderTexture _current;   // 本代读
RenderTexture _target;    // 本代写

void Step()
{
    _shader.SetTexture(_kernel, "_Source", _current);
    _shader.SetTexture(_kernel, "_Result", _target);
    _shader.Dispatch(_kernel, Mathf.CeilToInt(Width / 8f), Mathf.CeilToInt(Height / 8f), 1);
    (_current, _target) = (_target, _current);   // 交换角色，不搬运数据
}
```

同一次 Dispatch 内对同一纹理既读又写结果未定义，乒乓双缓冲是唯一的正解。

### 5.2 kernel 契约（基础版）

```hlsl
#pragma kernel Step
#pragma numthreads(8, 8, 1)

RWTexture2D<float4> _Result;
Texture2D<float4>   _Source;
uint  _Width, _Height;
float _Wrap;      // 1 = 环面，0 = 死边界

[numthreads(8, 8, 1)]
void Step(uint3 id : SV_DispatchThreadID)
{
    // 越界守卫：线程组覆盖会超出网格，越界线程必须直接返回
    if (id.x >= _Width || id.y >= _Height) return;

    uint alive = 0;
    for (int dy = -1; dy <= 1; ++dy)
    for (int dx = -1; dx <= 1; ++dx)
    {
        if (dx == 0 && dy == 0) continue;
        int2 p = int2(id.xy) + int2(dx, dy);
        if (_Wrap > 0.5)
            p = (p + int2(_Width, _Height)) % int2(_Width, _Height);
        else if (p.x < 0 || p.y < 0 || p.x >= _Width || p.y >= _Height)
            continue;

        alive += _Source.Load(int3(p, 0)).r > 0.5 ? 1 : 0;
    }

    uint self = _Source.Load(int3(id.xy, 0)).r > 0.5 ? 1 : 0;
    bool next = self == 1 ? (alive == 2 || alive == 3) : (alive == 3);
    _Result[id.xy] = next ? 1.0 : 0.0;      // 存活写 1.0（8 位 UNORM 下即 255）
}
```

三处必须注意：

1. `if (id.x >= _Width || id.y >= _Height) return;` —— 线程组按 8 取整，越界写入会静默破坏数据；
2. 存活值写 `1.0` 而不是整数 `1` 的语义混淆；CPU 侧用 `Color32` 写初始图案时同理，必须写 `255`；
3. `Load` 用整数坐标采样，避免采样器的插值与边界行为介入，边界完全由代码控制。

### 5.3 三档优化

| 档 | kernel 变化 | 资源变化 |
|---|---|---|
| 一 ✅ | (TILE+2)² 载入 `groupshared` + `GroupMemoryBarrierWithGroupSync()`，邻居从共享内存读 | 不变 |
| 二 ✅ | 每个 texel 的 RGBA 四通道各表示一个细胞，邻居统计按通道求和 | 纹理宽度减到 1/4，线程数减到 1/4 |
| 三 ✅ | `RWTexture2D<uint>`，1 字 = 32 细胞，位并行加法统计邻居 | 显存降约 32 倍，另需展开 kernel 供显示 |

三档共用 `IGridKernel` 与显示路径，切换档位只换 kernel 与纹理布局，控制层不感知。

档一有两个实现细节值得单独记一笔，它们都是"能跑但结果会错"的坑：

- **屏障必须被整组线程执行到**，所以越界线程的 `return` 放在 `GroupMemoryBarrierWithGroupSync()` **之后**。放在前面会导致组内线程数不一致，行为未定义（可能直接挂住）。
- **halo 的越界处理必须与边界语义一致**：环面模式下取对侧数据，死边界模式下取 0。搞错的表现是"画面中间正常、接缝处出错"，非常难定位。

档位通过 `GpuGridKernel` 构造参数选择，线程组大小随档位变化（基础版 8×8，档一 16×16），Dispatch 的组数按对应尺寸向上取整。

**档一 halo 载入的实现选择**：不用"扁平下标 + 整数除/取模"，而用按行列步进的双层循环（每个线程负责 `tid.y` 与 `tid.y+TILE` 两行、`tid.x` 与 `tid.x+TILE` 两列，组合起来恰好覆盖全部 18×18 格且不重复）。原因是 D3D11 会把有符号整数除法与取模编译成一长串指令并给出编译器警告——这个警告最初同时出现在 Step / StepShared / StepPacked / StepBitPacked 四个 kernel 上（共 8 条），修完后着色器编译零警告。

### 5.5 档二（四通道打包）的三个坑

这三处都是"能编译、能跑、结果错"的类型，实际开发中全部被一致性测试抓出来：

1. **纹理尺寸必须用纹理宽而不是网格宽。** 档二的状态纹理宽度是网格宽度的 1/4。第一版漏改了这一处，纹理被建成 32×32 而 kernel 按 8×32 的语义写入，回读时只检查了前 8 列——回读出来的"人口数"恰好等于 8×32=256，一个看起来很合理的数字。**错误的数字未必离谱，只有与参考实现比对才会暴露。**
2. **死细胞的 alpha 必须是 0。** 基础版与档一只读 `.r`，所以把死值写成 `(0,0,0,1)` 一直没问题；但档二把 alpha 通道也当作细胞，于是所有死细胞都被读成活的，整片棋盘凭空多出生命。现在 compute 里的 `DEAD` 统一为 `(0,0,0,0)`。
3. **本行求和必须排除细胞自身。** 上一行/下一行取左中右三格，本行只能取左右两格；写成三格就把自己算成了邻居，每个细胞的邻居数都多 1，规则随之全部走样。基础版与档一由 `dx == 0 && dy == 0` 的跳过保证这一点，打包版没有天然的结构来保证，只能靠写法正确。

另外，档二有一个**明确的适用前提**：网格宽度必须是 4 的倍数。宽度不是 4 的倍数时尾部会出现填充通道，"按细胞回绕"与"按 texel 回绕"不再等价。当前做法是在构造时直接拒绝（`ArgumentException`），由 `GridKernelFactory` 降级到档一并给出提示——**宁可退一档，也不给出看起来正常的错误结果**。

### 5.6 档三（位打包）的实现要点

**布局**：1 个 `uint` 承载 32 个细胞，状态纹理宽度 = 网格宽 / 32，因此纹理是整型的（`GraphicsFormat.R32_UInt`），不能直接用于显示。

**邻居统计走位并行**（不是逐格 popcount）：

1. 对每一行取左、中、右三个字，算出"左邻掩码 / 自身 / 右邻掩码"；
2. 用全加器把三个 0/1 操作数压成 2 位计数：低位 = 三者异或，高位 = 三者多数；
3. 本行只取左右，排除细胞自身（与基础版 `dx==0 && dy==0` 的跳过等价）；
4. 把三行的 2 位计数逐位平面相加，得到每格 0~8 的邻居数，再逐位应用 B3/S23。

**跨字边界**（本档最容易写错的地方）：左移要从上一个字的最高位补入，右移要从下一个字的最低位补入；环面模式下第一个字与最后一个字互相补位，死边界模式下该补位为 0。

**适用前提**：网格宽度必须是 32 的倍数。否则每行最后一个字会出现无效位，跨字移位与回绕的边界会整体偏离一位。构造时直接拒绝，由工厂降级到档二或档一。

**显示与回读**：位打包纹理不能直接显示，`ExpandBitPacked` 把它展开成 1 texel = 1 细胞的常规纹理。展开是**按需**的（`_expandedGeneration` 与当前代数比对，每代最多一次），不会在每帧重复付出代价。

**开发中踩到的坑**：盖印时忘记把状态纹理绑到 `_StatePacked`（仍绑着 `_State`），kernel 于是往一个没绑定的纹理写数据。**这种错误不会报任何警告，表现是人口数恒为 0**——又是一次只有与参考实现比对才能发现的问题。

### 5.4 盖印构型到 GPU 纹理

设计阶段考虑的方案是"CPU 侧建 `Texture2D` 再 `Graphics.CopyTexture` 到目标 RT"，理由是盖印坐标最容易写错，放 CPU 侧好测。

实现时改成了**坐标缓冲 + 盖印 kernel**（`StructuredBuffer<int2>` + 逐点写入），原因是一个接口语义上的真实冲突：
`IGridKernel.StampPattern` 的语义是"把构型追加到当前状态上"，而 `CopyTexture` 是整张覆盖。
要在 CPU 侧用 CopyTexture，就必须在 CPU 上维护一份完整的棋盘状态才能重建整张纹理——
那等于把模拟状态复制一份到 CPU，GPU 路径的意义被削掉一半。

改成 kernel 逐点写入后，语义与 CPU 路径完全一致。**可测试性也没有丢**，只是换了做法：
坐标合成与越界校验抽到了 `PatternStamp`，CPU 与 GPU 两条盖印路径共用同一份实现，
越界一律抛异常（不静默裁剪）——"两边各自算一遍坐标"这种隐性分歧从结构上被消除了。

本次改动是设计文档与实现不一致时的正确处理：以接口语义为准调整实现，并把原因写回文档。

## 6. 显示与控制层【已实现】

- **显示**：状态纹理挂在 uGUI 的 `RawImage` 上（`uvRect` 处理 Y 方向），而不是自建面片材质。
  选择 uGUI 的原因：URP 2D 渲染器下它的显示路径最稳，且不需要额外写着色器；
  纹理本身仍是 `FilterMode.Point` + 无 mipmap，避免模糊与摩尔纹。
- **URP 注意事项**：URP 下 `OnRenderImage` / `Graphics.Blit` 到屏幕不生效，因此不使用这两者。
- **调速**：累加器驱动，而不是每帧固定一代。

```csharp
_accumulator += Time.unscaledDeltaTime;
int budget = MaxStepsPerFrame;                 // 防止高速档卡死主线程
while (_accumulator >= _stepInterval && budget-- > 0)
{
    _accumulator -= _stepInterval;
    _kernel.Step();
}
```

- **状态显示**：用 `TryDetectPeriod` 在后台低频分析，界面显示"当前构型、周期、每周期位移"，把"循环震荡"从观感变成可读的数字。

### 6.1 构型分析：把题目要求变成屏幕上的数字

`LifeController.AnalyzeCurrentPattern()` 做的事情，就是把测试里那套判定搬到运行时：

1. 取当前状态快照（GPU 路径一次回读）；
2. 载入 CPU 参考实现（`GridModel.LoadFrom`）；
3. 向前演化 `max(maxPeriod×2, 4)` 代，记录每代快照；
4. 用 `PatternCompare.TryDetectPeriod` 算出周期与每周期位移；
5. 与构型声明比对，输出"稳定静物 / 振荡器 / 循环震荡（飞船）：周期 4，每周期位移 (1,-1) ✓ 一致"。

重置后会自动跑一次，因为那一刻局面是纯构型，分析最有意义。这条路径被 `AnalysisPath_SnapshotThenCpuThenDetect_RecoversGliderPeriod` 用例锁住——它与 GPU 路径共用同一批类型，回归时先在这里断。

**这个设计的价值**：题目要求"两种稳定、两种振荡、两种循环震荡"，肉眼只能看出"在动/不动"，而周期与位移是可直接读、可比对、可断言的量。把它放进界面，等于把验收标准做进了工具里。

### 6.2 编辑器工具

`LifeControllerEditor` 提供三块：

- **配置区**：ComputeShader、网格尺寸、环面开关、档位（附一句话说明各档的约束与代价）、播放参数、构型下拉（附分类/尺寸/细胞数/周期/位移摘要）。任一配置变化即重建内核，避免"改了参数但没生效"的错觉。
- **控制区**：播放/暂停、单步、重置、下一个构型、重新分析。快捷键同样可用：空格切换播放、`N` 下一个构型、`R` 重置、`→` 单步。
- **状态区**：实际内核（GPU 档位或 CPU 回退）、代数、活细胞数、检测周期，以及分析结论与降级提示。

两个实现细节值得记一笔：

1. **编辑器未运行时内核不创建**。`OnEnable` 里用 `Application.isPlaying` 把关，避免在编辑态分配 RenderTexture 后随域重载泄漏。面板会明确提示这一点，而不是让人对着没反应的按钮猜。
2. **快捷键必须走 Input System**。本项目 `activeInputHandler = 1`（仅新版 Input System），旧版 `UnityEngine.Input` 会直接抛 `InvalidOperationException`。代码用 `ENABLE_INPUT_SYSTEM` 条件编译 + `Keyboard.current == null` 守卫，换回旧版输入也不会报错。

### 6.3 随机初始状态（按种子）

需求是"按种子加载每个细胞的初始状态，然后看演化"。实现上有一个关键选择：**不用随机数生成器，而是用 `(seed, x, y)` 的纯哈希函数**。

原因是随机数生成器依赖调用顺序与内部状态：CPU 参考实现是逐行顺序遍历，GPU kernel 的线程执行顺序完全不同，用生成器两边必然对不上，"同一颗种子"就失去意义。纯哈希没有状态——谁在什么时候算、算多少次，结果都一样。

代价是要在 C# 与 HLSL 里各写一份相同的整数哈希，并保证逐位一致。为此设了三层锁定：

1. **黄金值锁住 C#**：`RandomFieldTests.Hash_MatchesIndependentReferenceValues` 的期望值由独立的 Python 实现算出；
2. **聚合校验**：64×64 / seed=20260917 / 密度 0.32 的活细胞数必须是 **1295**（同样由 Python 独立算得），这条比单点哈希更强，因为它同时约束了整张棋盘；
3. **GPU 逐位比对**：同一种子下 GPU 填充结果与 CPU 逐位相同（`RandomFill_GpuMatchesCpu`，四档各一条）。

哈希只用 `uint` 的乘法、异或与右移，都是精确定义的定点运算；存活判定也比较整数阈值，避免"浮点除法在两边舍入不同"导致的偶发不一致。

随机汤顺带是很强的压力测试：密度高、结构混乱，边界与跨字都会被频繁命中。因此 `RandomSoup_GpuMatchesCpu_EveryGeneration` 会让它连续演化 9 代、逐代比对哈希——这比稀疏构型更能暴露批量数据里的问题。

## 7. 已知坑清单

| # | 坑 | 后果 | 规避 |
|---|---|---|---|
| 1 | 8 位 UNORM 纹理上写入整数 `1` | 实际存 1/255，判活阈值 `>0.5` 全部不成立，画面全黑 | 存活写 `1.0`；CPU 侧写 `Color32(255,…)` |
| 2 | 纹理 Y 轴方向与 quad UV 不一致 | 图案上下镜像，飞船反向飞 | 首版用不对称图案验证后再决定翻转位置 |
| 3 | Dispatch 覆盖超出网格 | 越界写入静默破坏数据 | kernel 首行做边界守卫；主机侧线程组数取 `ceil` |
| 4 | 死边界下飞船撞墙解体 | "循环震荡"不循环，直观上像 bug | 默认环面；死边界作为可选项 |
| 5 | `RenderTexture` 未 `Release` | 显存泄漏，Profiler 里持续增长 | 尺寸变更与 `OnDisable`/`OnDestroy` 时释放重建 |
| 6 | `enableRandomWrite` 创建后不可改 | 运行时改属性无效 | 创建时就确定；尺寸变化重建纹理 |
| 7 | `Shader.Find` 在 build 中返回 null | 编辑器正常、打包后黑屏 | 显示材质用序列化引用 |
| 8 | 位打包跨字边界 | 档三结果整体偏移一列 | 与档一逐代哈希比对 |
| 9 | 网格尺寸非 8/32 倍数 | 线程组越界或行尾填充错位 | 尺寸取整处理；用 37×11 这类尺寸做测试用例 |
| 10 | 有符号整数取模 / 除法 | D3D11 上会被编译成一长串指令，触发编译器警告并拖慢 kernel | 邻居回绕改用条件加减（偏移不超过 ±1 格）；halo 载入改用按行列步进的双层循环 |
| 11 | 带提前 `return` 的小工具函数 | D3D11 编译器无法证明所有路径都有返回值，在每个调用点报 "use of potentially uninitialized variable" | 改写成单个表达式返回 |
| 12 | 显示尺寸写死为固定像素 | 不同分辨率下要么太小、要么被裁掉；不加比例约束又会把正方形网格拉变形 | 视口容器占屏幕 90% + `AspectRatioFitter(FitInParent)` |
