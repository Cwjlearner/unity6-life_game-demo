# 康威生命游戏（Unity 6）

笔试题目实现：Conway's Game of Life。计算走 ComputeShader + 乒乓纹理，提供**四种数据布局**（基础版 + 三档递进优化），并配一套 CPU 参考实现作为正确性基线与无 GPU 环境的回退路径。

题目要求"2 种稳定状态 + 2 种震荡状态 + 2 种循环震荡状态"与"考虑实现效率"，两者都被做成了**可断言的测试**，而不是靠肉眼观察。

---

## 快速开始

0. 克隆后用 Unity Hub 的「Add project from disk」指向本目录。
1. 用 Unity 6（本工程为 6000.4.12f1）打开。**首次打开需要重新导入资源并编译脚本，约 1~3 分钟**——`Library/`、`Logs/`、`Temp/` 等生成目录不在版本库里（见 `.gitignore`），Unity 会自动重建。
2. 菜单 **GameOfLife → 打开演示场景**（场景缺失时会自动生成）。
3. 按 **Play**。

默认是 Glider 在 64×64 环面网格上以 12 代/秒演化（网格取小是为了让构型在屏幕上看得清，见下文"画面太小/太大"）。

**打开场景后 Hierarchy 里应该看到**：

```
Main Camera
Canvas
  └ LifeView       ← 画面显示（RawImage）
GameOfLife        ← 选中它，检视面板就是控制台
```

> 工程里另有一个 `Assets/Scenes/SampleScene.unity`，那是 URP 2D 模板自带的空场景（只有相机和 2D 灯光），**里面没有 `GameOfLife` 物体**。演示相关内容全部在 `LifeDemo.unity`。
>
> 为避免搞混，生成演示场景时已经把 `LifeDemo` 设为 Play 模式的起始场景——无论当前打开哪个场景，按 Play 都会进演示场景。

## 怎么看效果

| 想看的现象 | 怎么操作 |
|---|---|
| 稳定静物（不变化） | 构型选 `Block` 或 `Beehive`，连续多代后形状纹丝不动 |
| 振荡器（往复） | 选 `Blinker` 或 `Toad`，每 2 代回到原形 |
| 循环震荡 / 飞船 | 选 `Glider` 或 `LWSS`，形状每 4 代平移一次而不复原位 |
| 随机初始状态的演化 | 点 **按种子随机填充**（或 **换种子并填充**），看随机汤演化出稳定块、振荡器与滑翔机 |
| 边界语义的影响 | 关掉 Inspector 的"环面边界"，看滑翔机撞墙解体；打开后它会绕回来 |
| 性能档位的差别 | 切换"档位"，看状态区显示的"实际内核"；网格调到 1024² 以上差异更明显 |

**操作入口**（场景中 `GameOfLife` 物体上的检视面板）：

- 构型下拉（6 种，附分类/尺寸/细胞数/周期/位移摘要）
- 播放/暂停、单步、重置、下一个构型、重新分析
- 代数/秒、每帧步数上限、网格尺寸、环面开关、档位
- 随机初始状态：种子（整数）+ 存活密度（默认 0.32），配"按种子随机填充"/"换种子并填充"
- 状态区实时显示：实际内核、代数、活细胞数、检测周期、构型分析结论

**快捷键**：`空格` 播放/暂停、`N` 下一个构型、`R` 重置、`→` 单步。

**画面太小 / 太大**：单个细胞占多大由网格尺寸决定。默认 **64×64**，此时一个滑翔机约占画面的 5%，看得很清楚；想看随机汤或大网格演化就调到 256/512/1024，细胞会随之变小。显示区域做了比例适配，会尽量铺满屏幕且不会被拉变形。

### 想跑随机模拟（不用预制构型）

把检视面板里的 **初始状态来源** 改成下面两项之一，然后按 Play 或点「重置」：

| 选项 | 行为 |
|---|---|
| **随机 · 固定种子（可复现）** | 用「种子」栏里的那颗种子生成棋盘。同一颗种子永远得到同一张棋盘，方便复现和对比 |
| **随机 · 每次换种子（真随机）** | 每次重置 / 每次 Play 都换新种子，局面每次都不一样 |

初始存活密度用「存活密度」调（默认 0.32，低于 0.2 太稀疏、高于 0.5 会迅速塌缩，**0.3 左右最有趣**）。另外「按种子随机填充」和「换种子并填充」两个按钮可以临时铺一次随机棋盘，不影响上面的设置。

> 随机局面不是单一构型，所以不会检出周期——这是预期的，状态区会说明原因。想看"周期 / 位移"读数就切回预制构型。

**画面上下颠倒时**：勾选 `GameOfLife` 物体上 `LifeDisplay` 的 `Flip Y`。纹理与屏幕的 Y 方向约定在不同图形 API 下不同，这个开关就是为此留的。

## 调整与检验

### 在场景里检验（最快）

点 Inspector 的 **重新分析**。它会把当前状态取回 CPU 参考实现向前推演，用与测试相同的逻辑算出周期与位移，并和构型声明比对，例如：

```
循环震荡（飞船）：周期 4，每周期位移 (1,-1)（Glider 声明周期 4，位移 (1,-1)）✓ 一致
```

如果显示 `⚠ 与声明不一致`，说明实现或构型数据有问题。

**随机初始状态也可以检验**：同一个种子在 CPU 与 GPU 上必须得到**逐位相同**的棋盘。这条由 `RandomFill_GpuMatchesCpu`（四档各一条）把关；`RandomSoup_GpuMatchesCpu_EveryGeneration` 还会让随机汤连续演化 9 代，逐代比对哈希。

### 跑测试（真实验证）

> 需要先关闭 Unity 编辑器，否则项目被锁，命令会直接失败。

```powershell
& "G:\unity\Editor\Unity.exe" -batchmode `
  -projectPath "F:\unity_project\My project" `
  -runTests -testPlatform EditMode `
  -testResults "F:\unity_project\My project\TestResults-EditMode.xml"
```

预期：`total=88 passed=88 failed=0`。注意 `Unity.exe` 是启动器，命令会立即返回，真正的工作在后台进程里，请等结果文件生成（首次约 1 分钟）。

去掉 `-nographics` 才会真正执行 GPU 一致性用例（加 `-nographics` 时它们会跳过，因为该模式没有图形设备）。

### 独立验证构型数据

```powershell
python tools\verify_patterns.py
```

预期输出末尾为"分类统计：静物 2 / 振荡器 2 / 飞船 2（题目要求 2/2/2）"。

### 重建演示场景

## 6 种预制构型

坐标、周期、位移由 `tools/verify_patterns.py` 独立模拟得出（不引用 C# 代码），再由 Edit Mode 测试在 C# 实现上复验。

| 名称 | 分类 | 包围盒 | 细胞数 | 周期 | 每周期位移 |
|---|---|---|---|---|---|
| Block | 稳定静物 | 2×2 | 4 | 1 | — |
| Beehive | 稳定静物 | 4×3 | 6 | 1 | — |
| Blinker | 振荡器 | 3×1 | 3 | 2 | — |
| Toad | 振荡器 | 4×2 | 6 | 2 | — |
| Glider | 循环震荡（飞船） | 3×3 | 5 | 4 | (1, −1) |
| LWSS | 循环震荡（飞船） | 5×4 | 9 | 4 | (−2, 0) |

除此之外还有**按种子生成的随机初始状态**：细胞存活与否由 `(seed, x, y)` 的整数哈希唯一决定，不依赖随机数生成器的调用顺序，因此同一颗种子在任何机器上都得到同一张棋盘，且 CPU 与 GPU 两条路径逐位一致。默认密度 0.32，接近最容易演化出丰富结构的临界值。

## 四档性能

中位数，步数 120，预热 20，重复 3 次，单位 ms/代（数值越低越快）：

| 网格 | 基础版 | 档一 共享内存 | 档二 四通道打包 | 档三 位打包 |
|---|---|---|---|---|
| 256² | 0.0268 | 0.0155 | 0.0111 | **0.0101** |
| 512² | 0.0756 | 0.0325 | 0.0206 | **0.0169** |
| 1024² | 0.2641 | 0.0981 | 0.0559 | **0.0471** |
| 2048² | 0.9043 | 0.3725 | 0.2005 | **0.1726** |

> 同一配置在不同轮次之间约有 10~20% 波动（受机器负载影响），因此请按**趋势与量级**读这张表，不要当成精确值。结论（档三最快、档二性价比最高、加速比随网格增大）在多次运行中稳定成立。

| 档位 | 每个承载单元 | 网格宽度约束 | 适用场景 |
|---|---|---|---|
| 基础版 | 1 细胞 / texel | 无 | 教学、调试、CPU 回退 |
| 档一 共享内存 | 1 细胞 / texel | 无 | 通用优化，无尺寸限制 |
| 档二 四通道打包 | 4 细胞 / texel | 宽 % 4 == 0 | **默认**：接近最快且约束宽松 |
| 档三 位打包 | 32 细胞 / uint | 宽 % 32 == 0 | 超大网格 / 显存受限（显存降 32 倍） |

约束不满足时 `GridKernelFactory` 会自动降级并在检视面板给出提示，而不是给出看起来正常的错误结果。

## 怎么保证是对的

三层验证，缺一不可：

1. **规则穷举**：3×3 邻域一共只有 512 种组合，测试逐一比对中心细胞的下一代状态与教科书上的 B3/S23 是否一致（`Rule_IsExhaustivelyCorrect_ForAll512Neighbourhoods`）。这等价于把规则表逐行核对，而不是挑几个例子。
2. **CPU 参考实现**（`GridModel`，逐格 8 邻域，刻意写得朴素可读）作为正确性基线。
3. **逐代哈希比对**：GPU 每跑一代回读状态，与 CPU 参考实现比对哈希与活细胞数。四档 × 4 种网格尺寸全部一致，另有随机汤连续 9 代逐代比对。这一层抓出过三个"能编译能跑但结果错"的 bug。
4. **独立模拟器**：`tools/verify_patterns.py` 用 Python 重写一遍规则，为构型数据提供来自实现之外的证据；它抓出过一条手算错误的期望值。随机哈希同样有独立算得的黄金值，形成 Python → C# → HLSL 的三方锁定。

**为什么这足以说明 GPU 也是对的**：CPU 侧对 512 种邻域穷举正确（第 1 条），而 GPU 与 CPU 逐位相同（第 3 条）——两条合起来，GPU 的规则就是教科书规则。

性能侧同样有门槛：基准用例断言"四档终态哈希一致"与"任何一档不超过基础版耗时的 1.15 倍"。

## 已知约束

- 档二要求网格宽度是 4 的倍数，档三要求是 32 的倍数；不满足时自动降级。
- 无 ComputeShader 支持的平台（如 WebGL）自动回退 CPU 参考实现，界面与控制逻辑不变。
- GPU 一致性测试需要图形设备；`-nographics` 批处理下会跳过（该模式顺带验证了 CPU 回退路径可用）。
- 编辑器未运行时不会创建内核（避免 RenderTexture 泄漏），因此检视面板的控制按钮与状态读数只在 Play 模式下有效。
