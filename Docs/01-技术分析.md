# 康威生命游戏（Unity 6）——技术分析

> 状态标记：**【已实现】** 代码已在仓库中并通过验证；**【设计中】** 方案已定，代码待写；**【待实测】** 需要 Profiler 数据回填。
> 最后更新：2026-09-17

## 1. 问题与约束

**功能约束**

- 必须实现 2 种稳定状态、2 种震荡状态、2 种循环震荡状态（共 6 种构型），并实时可视化其演化。
- 控制需求：启动/暂停、单步、切换构型、重置、调速。

**非功能约束**

- 进阶要求是"考虑实现效率"。这条要求在笔试语境下有双重含义：既要真的快，也要能**说清楚为什么快、快多少**。因此本项目的性能部分不是"用了 GPU"，而是"三种数据布局的对比 + 可复现的测量方法"。
- 交付形态未指定平台。WebGL 不支持 ComputeShader，因此**必须保留 CPU 回退路径**，否则方案会在未知的评审环境里直接失效。

## 2. 候选方案对比

生命游戏的性质：每代每个细胞的计算只依赖 3×3 邻域，是典型的 **2D stencil**，天然适合并行；瓶颈在内存流量而非算术。

| 方案 | 单代复杂度 | 实现难度 | 可测试性 | 平台风险 | 结论 |
|---|---|---|---|---|---|
| **A. CPU 朴素数组**：`bool[]` + 逐格 8 邻居 | O(W·H) 次内存访问 | 极低 | 极高（纯 C#，可脱离引擎测） | 无 | 作为**正确性基线**保留 |
| **B. CPU 位并行**：1 个 `ulong` = 64 个细胞，用移位 + 进位加法统计邻居 | 相比 A 快 1~2 个数量级 | 高（跨字边界处理易错） | 高 | 无 | 未采用（见 §3.3） |
| **C. GPU 纹理采样**：1 texel = 1 细胞，逐 texel 采样 8 邻域 | O(W·H) 次采样，但由 GPU 并行 | 中 | 中（需回读比对） | 低（DX/Metal/Vulkan 均支持） | **主路径** |
| **D. GPU 位打包**：1 个 `uint` = 32 细胞 | 相比 C 内存流量降约 32 倍 | 高 | 中 | 低 | 作为**档三**实现并与 C 交叉验证 |

## 3. 决策与理由

### 3.1 主路径选方案 C（GPU 纹理采样 + 乒乓纹理）

**决策**：演化逻辑放在 ComputeShader，状态存在两张同规格 `RenderTexture` 中乒乓交替；显示直接用当前纹理采样到面片。

**理由**

1. **契合题目语义**。题目强调"实时可视化展示每种构型演化效果"，纹理既是计算载体也是显示载体，省掉一次 GPU→CPU→GPU 的数据搬运。若把状态放在 CPU 数组，每代都要上传纹理，带宽反而成为新瓶颈。
2. **读-写冲突有标准解法**。同一次 Dispatch 内读写同一纹理结果未定义，乒乓双缓冲把"读"和"写"分离到不同资源上，语义清晰。这是整个方案里唯一不能省的结构。
3. **可扩展**。档一/档二/档三三种优化都只是在同一套乒乓框架内替换 kernel 与数据布局，控制层与显示层不用改。

### 3.2 必须保留 CPU 路径（方案 A）

**决策**：`GridModel` 作为 CPU 参考实现长期保留，与 GPU 实现共用 `IGridKernel` 契约。

**理由**（这一条同时解决了三个问题，是本次设计里收益最高的决定）

- **正确性**：GPU 算错了画面往往"看起来还在动"，很难发现。有了参考实现，可以逐代比对哈希，把"像不像"变成"等不等"。
- **可测试性**：6 种构型的行为断言（周期、位移）可以完全脱离 GPU 运行，几毫秒出结果，不需要显卡也不需要渲染环境。
- **可用性**：不支持 ComputeShader 的平台（如 WebGL）自动降级，演示不会当场失败。

### 3.3 为什么不选方案 B（CPU 位并行）作为主路径

位并行（1 个 `ulong` 存 64 个细胞，用移位与进位加法统计邻居）在 CPU 上确实很快，但：

- 跨字边界的拼接逻辑复杂，出错后极难定位，收益却只是"CPU 更快"，而主路径本来就交给 GPU；
- 它的**思想**被方案 D 继承了——GPU 的档三就是同一套位并行思路搬到显存里。所以它没有被丢弃，而是被放在了更合适的位置。

### 3.4 边界条件：环面 vs 死边界（直接影响题目要求）

题目要求的第三类构型是"循环震荡（滑翔类）"。滑翔机在**死边界**下会撞墙解体，只有**环面**（上下左右回绕）才永不停歇。因此：

- 默认使用环面边界（`RenderTexture.wrapMode = Repeat`，kernel 内对邻居坐标取模）；
- 同时保留死边界开关，作为对照实验；这也让"边界条件如何影响结果"成为技术分析里可讲的一部分，而不是回避掉的细节。

## 4. 四种 GPU 数据布局（基础版 + 性能三档）

四种布局**都已实现并互相验证过**。它们共用同一套乒乓框架，区别只在 kernel 与资源布局。

| 布局 | 每个承载单元 | 状态纹理宽度（网格宽 W） |
|---|---|---|
| 基础版 | 1 个细胞 / texel | W |
| 档一 | 1 个细胞 / texel（邻居走共享内存） | W |
| 档二 | 4 个细胞 / texel | W / 4 |
| 档三 | 32 个细胞 / uint | W / 32 |

| 档 | 数据布局 | 每代全局内存读取 | 线程数 | 主要代价 |
|---|---|---|---|---|
| **一** | 1 texel = 1 细胞 + `groupshared` halo tile | 每线程组读取 (TILE+2)² 个 texel，而不是每线程 8 次采样，理论降至约 1/8 | W·H | 需要在共享内存中处理 tile 边界与 halo 越界 |
| **二** | 1 texel = 4 细胞（RGBA 各一个） | 纹理面积降为 1/4，线程数降为 1/4 | W·H/4 | 邻居统计要按通道聚合，边界处通道含义需固定 |
| **三** | 1 `uint` = 32 细胞（位打包） | 显存占用降约 32 倍 | W·H/32 | 跨字边界需拼相邻字；显示前需要额外的展开 kernel |

**档一的关键细节**：线程组先把 (TILE+2)² 的区域（含 1 圈 halo）载入 `groupshared`，同步后每个线程只从共享内存读取 8 个邻居。halo 的越界处理必须与边界语义一致——环面模式下 halo 要取对侧数据，否则会出现"中间正常、接缝处出错"的隐蔽 bug。

**档二的关键细节**：四通道打包后，"活细胞计数"变成对通道求和，必须避免通道间的相互污染；纹理宽度按 `W/4` 计算时，W 不是 4 的倍数要补齐。

**档三的关键细节**：位并行的正确性完全依赖跨字移位。左边界要用前一个字的最高位，右边界要用下一个字的最低位。这一档必须与档一逐代比对哈希，不能只靠肉眼看画面。

**档一实测**：相对基础版提升约 **1.8~2.5 倍**（网格越大越明显）。

**档二实测**：相对基础版提升约 **2.4~4.6 倍**，比档一还快 1.4~1.9 倍。

**档三实测**：四档中最快，但只比档二快 1.10~1.23 倍——32 倍的显存压缩并没有换回 32 倍的速度。数据与解释见 §6.2。

## 5. 正确性如何保证

### 5.1 把题目要求变成判等式

"稳定/振荡/循环震荡"在代码里必须是可以断言的式子，否则只能靠肉眼"看着像"：

| 行为 | 判定式 |
|---|---|
| 稳定静物 | `state(t) == state(t+1)` |
| 振荡器 | `state(t) == state(t+p)` 且 `state(t) != state(t+1)`，p > 1 |
| 飞船（循环震荡） | `state(t+p) == state(t)` **平移** `(dx,dy)`，且 `(dx,dy) != (0,0)` |

第三行是整个判定体系的关键：飞船**永远不会回到原位**，所以它不能用相等来判定，必须用"平移后相等"。能写出这条的差别，就是"做对了"和"看起来在动"的差别。

### 5.2 期望值来自独立实现，不是来自被验证的代码

6 种构型的周期与位移由 `tools/verify_patterns.py` 用 Python 重新实现规则后独立算出，再写进 C# 测试作为期望值。两条独立实现给出同一答案，才认为数据可信。

这不是形式主义——M1 阶段确实靠它拦下了一个错误：最初手算"3×3 实心块演化后只剩 4 个角"，独立模拟器给出 8 个细胞（漏算了紧贴四边的 4 个空位各恰好 3 个邻居而诞生）。如果直接照手算写测试，就会得到一条**错误的断言**，后续每次重构都要为它绕路。

**随机初始状态同理**：同一颗种子要求在 CPU 与 GPU 上得到逐位相同的棋盘，因此随机不能来自有状态的随机数生成器（两边线程顺序不同，必然对不上），只能来自 `(seed, x, y)` 的纯哈希。代价是 C# 与 HLSL 各要有一份相同的整数哈希——于是又形成一条锁定链：Python 独立实现给黄金值锁住 C#，GPU 一致性测试锁住 HLSL。

### 5.3 已实现的验证结果【已实现】

两层验证都已跑通：

| 验证层 | 覆盖内容 | 结果 |
|---|---|---|
| Unity Edit Mode 测试 | 规则语义、边界语义、快照往返与 GPU 行打包等价性、6 种构型行为、构型数据自检 | **39/39 通过**（0.07s） |
| .NET 独立运行验证器 | 同上逻辑的独立复算，用于在 Unity 不可用时快速迭代 | **71 项检查，0 失败** |
| Python 独立模拟器 | 构型坐标 / 周期 / 位移的 oracle | **符合题目要求（2/2/2）** |

其中"快照往返与 GPU 行打包转换等价性"用的是宽度 37 的网格（非 32 的倍数），专门覆盖行尾填充——这条是后续 CPU/GPU 交叉验证的地基。

### 5.4 GPU 与 CPU 的交叉验证【已实现】

GPU 路径每跑一代通过 `AsyncGPUReadback` 取回状态，用与 CPU 相同的 `GridSnapshot` 类型构造并比对哈希。

当前基础版已通过的用例：

| 用例 | 覆盖点 | 结果 |
|---|---|---|
| 6 种构型逐代哈希比对 | 静物 / 振荡器 / 飞船的完整演化过程（各 1~8 代） | ✅ |
| 37×23 网格（非 8 倍数） | 线程组取整、越界线程守卫生效、行尾不串数据 | ✅ |
| 死边界 + 角落滑翔机 | `_Wrap = 0` 分支：撞墙解体过程两侧一致 | ✅ |
| Clear 后归零 | 清零 kernel 与代数复位 | ✅ |
| 盖印后人口数 | 盖印 kernel 的坐标映射正确 | ✅ |

这套比对还顺带**排除了 Y 轴翻转的隐患**：如果 GPU 回读的行序与 kernel 的索引约定不一致，哈希必然对不上。既然逐代哈希全部相等，说明"texel(x,y) 与网格(x,y) 一一对应"这一约定在计算侧是自洽的，剩下的只是显示端的朝向问题（一个开关的事，不再影响正确性）。

回读是异步且昂贵的，**只用于验证与统计，不进每帧热路径**。

## 6. 性能如何量化

### 6.1 测量方法【已实现】

基准跑在 `StepBenchmarkTests` 里，可以在 CI 里重复执行，而不是手工看 Profiler 截图：

- **口径**：连续 120 次 Dispatch，末尾用一次同步回读（`AsyncGPUReadback.WaitForCompletion`）强制 GPU 执行完毕，统计平均每代墙钟时间。包含 CPU 提交开销，因此是**相对比较**而非纯 GPU 耗时。
- **交叉口径**：同一轮里再用 `ProfilerMarker` + `ProfilerRecorder` 记录纯 CPU 提交耗时，用来回答"瓶颈在提交侧还是执行侧"。
- **预热**：先跑 20 代并同步一次，把 compute shader 首次编译的开销排除在计时之外。
- **重复**：每个配置独立跑 3 次，取**中位数**。
- **环境**：`-batchmode` 无 VSync；不加 `-nographics`（否则没有 GPU）。

**为什么取中位数**：实测中同一配置出现过 0.29ms 与 0.55ms 两次相差近一倍的结果（机器负载波动）。单次采样会直接得出错误结论，中位数能稳定复现。

**回归门槛**：基准用例同时断言两件事——四档终态哈希一致（正确性），以及任何一档的耗时不超过基础版的 1.15 倍（性能）。四档在同一轮测量，机器负载对它们的影响是同向的，因此用相对比值做门槛比绝对耗时稳，不容易产生假失败。

用 Unity Profiler 的 GPU 模块做人工核对属于可选补充（需要编辑器交互，不进自动化）。

### 6.2 实测数据

四档对比（中位数，步数 120，预热 20，同一初始局面）：

| 网格 | 基础版 | 档一 groupshared | 档二 四通道打包 | 档三 位打包 | 档三 vs 基础 | 档三 vs 档二 |
|---|---|---|---|---|---|---|
| 256² | 0.0268 | 0.0155 | 0.0111 | **0.0101** | 2.65× | 1.10× |
| 512² | 0.0756 | 0.0325 | 0.0206 | **0.0169** | 4.47× | 1.22× |
| 1024² | 0.2641 | 0.0981 | 0.0559 | **0.0471** | 5.61× | 1.19× |
| 2048² | 0.9043 | 0.3725 | 0.2005 | **0.1726** | 5.24× | 1.16× |

四档在 4 种尺寸下跑完 120 代后的状态哈希完全一致（基准用例会断言这一点），说明所有优化都没有改变语义。

> 同一配置在不同轮次之间约有 10~20% 波动（机器负载），因此结论按**趋势与量级**读。本表取自 M6 那一轮；M8 收尾时复跑的数值（如 2048² 档三 0.1483 ms）与表中同量级，相对关系不变。

**显存占用对比**（以 2048²、双缓冲合计计）

| 档位 | 每个承载单元 | 单张状态纹理 | 双缓冲合计 |
|---|---|---|---|
| 基础版 / 档一 | 1 个细胞 / texel | 16 MB | 32 MB |
| 档二 | 4 个细胞 / texel | 4 MB | 8 MB |
| 档三 | 32 个细胞 / uint | 0.5 MB | 1 MB |

**怎么读这组数据**

1. **档一的收益约 2.5×，不是"全局读取降为 1/8"推导出的 8×。** 瓶颈已不完全是显存带宽——dispatch 提交、ALU、纹理 `Load` 的访存延迟与固定开销都在分摊。把理论收益当成实际收益，是性能优化里最常见的自欺。
2. **档二在所有尺寸上都赢，而且赢得比预期多。** 设计阶段的判断是"档二在小网格上可能因调度开销而收益不明显"，实测被推翻：256² 上它仍比档一快 1.40×。回头看原因：档二不只是"纹理变小"，它把**每 4 个细胞的邻居读取从 32 次降到 9 次**（每个 texel 一次 `float4` Load 覆盖 4 个细胞），同时线程数降到 1/4、纹理足迹降到 1/4（缓存命中更好）。这三件事在 256² 上依然成立，小网格并没有抵消它们。
3. **档三最快，但增益与压缩比严重不成比例。** 它把显存降了 32 倍、线程数降了 32 倍，速度却只比档二快 1.10~1.23 倍。原因不难推：档二之后瓶颈已不在显存容量或线程调度，而在位并行本身增加的 ALU 工作量（每行 3 次 Load + 多个位平面全加器）以及 dispatch 的固定开销。**"压得更小"不等于"跑得更快"，这一点在档三上体现得最清楚。**
4. **档三真正的价值是显存占用**：2048² 下从 32 MB 降到 1 MB。它适用于显存受限的设备或超大网格；在 256² 这种演示尺寸上，省下的内存并不解决任何实际瓶颈。
5. **档二的性价比最高**：四种尺寸下都接近最快，适用前提最宽松（宽度是 4 的倍数），且显示路径不需要额外的展开通道。因此演示默认使用档二。

**CPU 提交耗时（同一轮测量，四档几乎一致）**

| 网格 | CPU 提交 ms/代 | 占档三墙钟的比例 |
|---|---|---|
| 256² | 0.0024 | 24% |
| 512² | 0.0022 | 13% |
| 1024² | 0.0025 | 5% |
| 2048² | 0.0028 | 2% |

这张表解释了两件事：

1. **优化的收益全部来自 GPU 侧。** 四档的 CPU 提交耗时都是约 2.4 µs/代，几乎与档位和网格大小无关；墙钟时间却从 0.010 到 0.90 ms 变化上百倍。所以档与档之间的差异不是"提交变快了"，而是"GPU 算得快了"。
2. **小网格的加速比被固定开销稀释。** 256² 上提交占了 24%，这部分成本不随优化下降，于是基础版→档三只快 2.65×；2048² 上提交只占 2%，加速比就上升到 5.24×。**这就是"小网格收益不如大网格"的量化解释**，比笼统地说"固定开销占比高"更有说服力。

### 6.3 选型建议

| 场景 | 推荐档位 | 理由 |
|---|---|---|
| 默认 / 通用演示 | **档二 四通道打包** | 接近最快（与档三差 10~16%），仅要求宽度是 4 的倍数，显示路径无需额外展开 |
| 超大网格 / 显存受限设备 | **档三 位打包** | 显存占用降 32 倍（2048² 下 32 MB → 1 MB），速度仍是最快 |
| 宽度不满足上述约束 | 档一 groupshared | 无尺寸约束，且明显快于基础版 |
| 教学 / 调试 / 无 GPU 环境 | **基础版 / CPU 参考实现** | 规则一眼可读，可断点、可脱离引擎测试 |

档二与档三的约束都不是"实现偷懒"，而是**没有它们就无法正确处理回绕**：档二要求宽度是 4 的倍数，否则填充通道会让按细胞回绕与按 texel 回绕不等价；档三要求 32 的倍数，否则每行最后一个字的无效位会让跨字移位整体偏移一位。这两种情况下工厂会自动降级并给出提示，而不是给出看起来正常的错误结果。

**被实测推翻的判断（保留记录）**

> 原判断："档二在同样网格尺寸下线程数更少、纹理更小，但在小网格上可能因调度开销而收益不明显。"
>
> 实测结果：档二在 256² 上比档一快 1.40×、比基础版快 2.37×，没有出现"小网格不划算"的现象。

保留这段记录的原因：优化前的直觉判断经常是错的，把预测与实测并列写下来，比只写一个漂亮结论更有价值。

**关于档三的预测与实测**

> 原判断："256² 的状态纹理只有 0.26 MB，本来就不构成显存压力；位打包的 32 倍压缩在这个尺度上没有意义，它的价值只在超大网格或显存受限场景。"
>
> 实测结果：**方向对，但"没有意义"说过头了。** 档三在 256² 上仍比档二快 1.10×，说明并非没有收益；只是收益远小于 32 倍的压缩比，其真正价值依然是显存占用而非速度。

## 7. 风险与缓解

| 风险 | 触发条件 | 缓解 | 结果 |
|---|---|---|---|
| 平台不支持 ComputeShader | WebGL / 老旧设备 | `SystemInfo.supportsComputeShaders` 守卫，自动切 CPU 路径 | ✅ 已实现 |
| 纹理 Y 轴方向不一致 | D3D/Metal 与 GL 约定差异 | 计算侧逐代哈希比对排除；显示端留 `FlipY` 开关 | ✅ 计算侧已排除，显示端待人工确认一次 |
| 线程组越界写坏数据 | 网格尺寸非线程组大小的倍数 | kernel 首行守卫 + 37×23 / 96×23 专项用例 | ✅ 已验证 |
| 位打包跨字错误 | 档三实现 | 与其余三档逐代哈希比对 | ✅ 已验证（96×23 覆盖每行 3 个字的跨字边界） |
| 打包与死值语义冲突 | 档二把 alpha 也当细胞 | 死值统一为 `(0,0,0,0)` | ✅ 被测试抓出并修正 |
| 演进步长与帧率耦合 | 高速档 | 累加器驱动 + 每帧步数上限 | ✅ 已实现 |
| 纹理格式精度问题 | 8 位 UNORM 上写入 `1` 实际存 1/255 | 存活值统一写 `1.0`（即 255） | ✅ 已规避 |

> 表格里"被测试抓出"的三条（档二纹理尺寸用错、死值 alpha、自身被算成邻居）都是能编译、能跑、结果错的类型，具体经过见实现文档 §5.5 与 §5.6。它们不是"设计阶段就想到的"，而是这套交叉验证机制的产出——这也是本方案坚持保留 CPU 参考实现的原因。

## 8. 结论

1. **题目要求被完整覆盖且可验证**：2 稳定静物 + 2 振荡器 + 2 飞船（循环震荡）共 6 种构型，其周期与位移由独立模拟器给出、由 61 条 Edit Mode 测试复验，运行时还会在界面上直接读数并标注是否与声明一致。
2. **效率做过四档对比，而不是"用了 GPU 就完事"**：从基础版到档三，2048² 网格下单代耗时 0.9043 ms → 0.1726 ms（约 5.2 倍），显存占用 32 MB → 1 MB（32 倍）。
3. **数据修正了三次直觉判断**，且都被保留在文档中：档二在小网格"可能不划算"（实测被推翻）、档三"在演示尺寸上没意义"（实测说过头了）、以及一条手算错误的构型期望值（被独立模拟器纠正）。
4. **压缩比不等于加速比**：档三把显存降 32 倍，速度只比档二快 1.10~1.23 倍。瓶颈从显存带宽转移到 ALU 与 dispatch 固定开销后，继续压缩数据不再有对等回报——这是本方案里最值得记住的一条结论。
5. **正确性靠机制而不是靠小心**：CPU 参考实现 + 逐代哈希比对 + 独立模拟器，三层里任何一层单独都不够，但合起来把"看起来在动"与"确实正确"分开了。
